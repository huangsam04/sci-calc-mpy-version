# 性能调优留痕（2026-07-23）

## 背景与范围

本次问题是从主菜单进入子页面时，左右滑动动画在开始前有明显停顿和掉帧感。审查范围为
`v1.1.3...HEAD` 中的性能改动，覆盖字体加载、部署格式、页面转场、函数面板、绘图缓存、
延迟持久化和实机基准。

这里的“导航首帧”是合成测试从调用 `Nav.go_to()` 到首次调用
`Nav.draw_transition()` 完成呈现的耗时。它包含目标页面激活和转场层捕获，但不包含解释器
上电、物理按键扫描和主循环事件分派。因此该指标用于比较固件内部导航路径，不应被表述为
完整的硬件冷启动时间。

## 定位结果

最初的 COM5 合成导航测量为：

| 指标 | 初始结果 | 结论 |
| --- | ---: | --- |
| 导航首帧 p95 | 498.059 ms | 卡顿主要发生在开始滑动前的同步工作。 |
| 转场帧 p95 | 21.788 ms | 连续帧合成本身不是首要瓶颈。 |
| FunctionPanel 捕获 | 494.061 ms | 进入函数面板时重新扫描并执行插件预览代码占主导。 |

函数面板把插件文件列表和描述移到启动期构建阶段。启动进度页仍可见时可以承受这部分工作，
而按键触发页面转场时不再执行。预加载后该页面的捕获测得约 100.554 ms；最终热态逐页测量
中，函数面板为 84.332 ms，其他页面约为 13.942 至 31.213 ms。

## 实现记录

### 转场路径

- [renderer.py](../source/ui/renderer.py) 在正常 `present()` 时把当前页面内容复制到既有的
  outgoing 缓冲区，并记录对应页面对象。
- 开始导航时，如果 outgoing 缓冲与当前页面匹配，则直接复用，不再同步绘制旧页面；只捕获
  即将进入的页面。该优化没有新增帧缓冲区。
- 转场合成仍使用现有的 `xtensawin` Viper 快路径。SSD1322 上全页滑动会改变几乎整个内容区，
  四像素列对齐还会扩大局部区域，因此没有引入脏矩形比较、缓存和额外 SPI 事务。

### 插件面板

- [function_panel.py](../source/screens/function_panel.py) 在构造时加载插件目录和描述，避免
  `activate()` 进入动画关键路径后执行 SD I/O 与插件源码。
- 插件在运行中被替换时，用户可在函数面板按 `Sh+ENT` 显式重扫。该操作故意由用户触发，
  这样普通进入页面仍保持响应。
- 代码注释说明了“启动期预加载”和“显式重扫”的边界，防止未来把插件执行重新放回转场路径。

### 其他性能项

- [xglcd_font.py](../source/display/xglcd_font.py) 使用构建期生成的紧凑 `.xglcd` 字体资产，
  不再在设备启动时解析 C 字体源码。
- [deploy.ps1](../deploy.ps1) 先用原生 `xtensawin` ABI 探针验证 `.mpy` 可导入，再部署核心
  模块；探针失败时回退到源码。所有上传运行时资产都会进行主机与设备的 SHA-256 比对。
- [plot.py](../source/screens/plot.py) 用四项 LRU 缓存复用编译后的表达式；函数注册表版本变化时
  自动失效，平移和缩放不会重复编译同一表达式。
- [storage.py](../source/utils/storage.py) 通过 `DeferredStorage` 把设置和变量写入移出按键关键
  路径，同时保留原有主文件、备份和临时文件的原子恢复机制。

## 审查与收口

代码审查发现并处理了两项问题：

| 审查发现 | 处理方式 |
| --- | --- |
| 插件目录只在启动时缓存，运行时替换 SD 内容后列表会过期。 | 增加 `Sh+ENT` 显式刷新，不把扫描重新放入普通转场。 |
| 原有 128 条原始帧样本会在 50 次导航中淘汰早期帧，可能遗漏偶发卡顿。 | [performance.py](../source/performance.py) 改为固定内存的帧耗时直方图，完整计入本轮每一帧。 |

帧直方图使用 128 个 0.5 ms 分桶，覆盖至 63.5 ms。超过该范围的慢帧进入最后一个桶；如果
p95 落在该桶，报告精确最大值而不是偏低的百分位。注释同时解释了这种设计：它不分配随帧数
增长的 Python 整数列表，又不会因为滑动窗口丢弃早期掉帧。

## 最终实机验证

2026-07-23，在已部署的 COM5 上执行预热后的 50 次页面往返：

| 指标 | 结果 |
| --- | ---: |
| 导航首帧 p95 / 最大值 | 115.817 ms / 147.471 ms |
| 转场帧 p95 / 最大值 | 28.499 ms / 86.327 ms |
| GC p95 / 最大值 | 23.747 ms / 23.747 ms |
| GC 后可用堆变化 | +10,256 字节 |
| 部署运行时资产 SHA-256 | 55 / 55 一致 |
| 运行时诊断 | `SELFTEST PASS failures=0` |

最大帧 86.327 ms 来自完整帧序列，而非只保留末段样本后的值。它保留为后续优化的真实基线；
当前改动优先消除了原先约 0.5 秒的按键后停顿，并没有把偶发长帧隐藏掉。

主机侧验证结果为 `check.ps1` 通过，包含 90 项 pytest、CPython 编译检查和 MicroPython
`xtensawin` `.mpy` 编译检查。部署时设备接受 ABI 探针并成功导入 `main.mpy`。基准与诊断完成
后已执行设备复位，恢复正常应用启动。

## 复现命令

在 `mp_version` 目录运行：

```powershell
.\check.ps1
.\deploy.ps1 -Port COM5 -Reset
..\.venv\python.exe -m mpremote connect COM5 exec `
  "import sys; sys.path.insert(0,'/sd'); import benchmarks; benchmarks.run(cycles=50)"
..\.venv\python.exe -m mpremote connect COM5 exec `
  "import sys; sys.path.insert(0,'/sd'); import diagnostics; diagnostics.run()"
..\.venv\python.exe -m mpremote connect COM5 reset
```

`mpremote exec` 会进入 raw REPL 并中断正在运行的应用，因此最后的 `reset` 是验证流程的一部分。

## 后续边界

- 当前帧 p95 约 28.5 ms，尚未达到 60 FPS 的 16.7 ms 预算。后续若继续优化，应先针对完整
  统计中出现的慢帧定位，而不是恢复脏矩形路径。
- 函数面板的热态捕获仍高于其他页面，因为它需要绘制多行较长的插件标签；但插件源码执行已
  不在普通导航路径中。
- 基准是只读合成导航，不写入用户设置或变量。真实按键端到端时延还会包含键盘扫描和主循环，
  应使用串口诊断或额外仪表单独测量。
